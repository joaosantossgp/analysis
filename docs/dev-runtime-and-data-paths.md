# Dev Runtime and Data Paths

## Active frontend

| Location | Purpose |
|----------|---------|
| `apps/desktop-web/` | Vite + React SPA — the only active frontend |
| `apps/desktop-web/src/` | TypeScript/TSX source |
| `apps/desktop-web/dist/` | Built static bundle (gitignored; generated by `npm run build`) |

Do not modify code under `apps/api/` for desktop work — that is a separate FastAPI service.

## Active backend / bridge

| Location | Purpose |
|----------|---------|
| `desktop/app.py` | pywebview entry point; path setup; window creation |
| `desktop/bridge.py` + `desktop/bridge_api/` | `CVMBridge` public entry point and domain mixins exposed to the JS frontend |
| `src/platform/settings.py` | All path resolution logic (`AppPaths`, `build_settings()`) |

## Data directory — release app

The packaged release app (`CVMAnalytics.exe`) stores all runtime data under:

```
%USERPROFILE%\Documents\CVMAnalytics\
├── db\
│   └── cvm_financials.db      ← SQLite database
├── output\                    ← Excel exports
├── logs\                      ← Refresh logs
├── cache\                     ← Active universe cache, health snapshots
└── backup\                    ← Automatic pre-migration backups
```

This path is resolved by `_user_data_root()` in `desktop/app.py` and injected as
`CVM_DATA_DIR` (and related `CVM_*` vars) by `_configure_bundled_data_paths()`,
which only runs when `sys.frozen=True` (packaged build).

Override with `CVMANALYTICS_DATA_DIR` env var to redirect the release app to a
different location (useful for staging or operator installs).

## Data directory — dev mode (default: shared Documents data)

When running `python -m desktop.app --dev`, the app uses the same user-visible
data root as the packaged release app:

```
%USERPROFILE%\Documents\CVMAnalytics\
├── db\
│   └── cvm_financials.db
│   └── energy_kpis.db
├── output\
├── logs\
├── cache\
└── raw\
```

This keeps dev lookups aligned with the real database used by the `.exe`.

In dev, `desktop.app` sets `CVMANALYTICS_USE_RELEASE_DATA=1` automatically when
it points at Documents. The Status page shows the shared-data warning and
destructive bridge actions remain blocked unless explicitly allowed.

`CVM_DATA_DIR` takes precedence. Set it explicitly when you need a sandbox or
isolated fixture data.

## Dev commands

### Default dev (shared Documents data)

```powershell
# From repo root
python -m desktop.app --dev

# Or use the convenience script
.\scripts\release\dev-desktop.ps1
.\scripts\release\dev-desktop.ps1 --debug    # opens DevTools
```

Data lives in `%USERPROFILE%\Documents\CVMAnalytics\` — same as the release app.
Writes are blocked by default in dev shared-data mode.

### Dev with custom data directory

```powershell
$env:CVM_DATA_DIR = "C:\path\to\your\test-data"
python -m desktop.app --dev
```

Use this for isolated dev data, destructive experiments, or fixtures that must
not touch the shared Documents database.

### Vite-only (browser preview, no bridge)

```powershell
cd apps/desktop-web
npm run dev
```

Opens `http://127.0.0.1:5173` in a browser. The pywebview bridge
(`window.pywebview.api`) is **not available** in this mode — all bridge calls
will fail silently or show browser fallback UI. Use this only for styling/layout
work that does not require data.

### Vite-only with mock bridge (browser preview + fixture data)

```powershell
cd apps/desktop-web
npm run dev:mock
```

Runs the Vite dev server with `VITE_MOCK_BRIDGE=1`. All `callBridge()` calls are
routed to an in-process fixture implementation (`src/lib/bridge/mock.ts`) instead
of `window.pywebview.api`. The fixture provides:

- 6 companies: complete, partial, failed, no_history, and unmapped variants
- One running and one completed refresh job
- Financial KPIs and statement matrices for two companies
- Base health snapshot at 70% coverage
- Onboarding state (completed), update settings, sector directory

**This mode is dev-only.** The mock bridge module is dead-code-eliminated from
production builds (Vite tree-shakes `import.meta.env.DEV === false` paths). A
runtime guard inside `mock.ts` also throws if somehow loaded in a non-dev build.

The Status strip shows **BRIDGE · MOCK** in violet and the Status page shows
`Mode: mock (fixture)` in the Runtime card.

## Environment variables

| Variable | Default (dev) | Purpose |
|----------|---------------|---------|
| `CVM_DATA_DIR` | `%USERPROFILE%\Documents\CVMAnalytics` | Root data directory (all modes); set explicitly for isolated data |
| `CVMANALYTICS_USE_RELEASE_DATA` | `1` in desktop dev shared-data mode | Marks dev as using the release Documents path |
| `CVMANALYTICS_ALLOW_RELEASE_DATA_WRITES` | — | Set to `1` to allow destructive bridge calls in dev+release-data mode (normally blocked) |
| `CVMANALYTICS_CONCURRENT_LOCK_DETECTED` | — | Set automatically at startup when another process holds the same data directory lock; forces read-only mode |
| `CVMANALYTICS_DATA_DIR` | — | Override data root for the packaged release app |
| `CVM_DB_DIR` | `{data}/db` | Override DB directory |
| `SQLITE_PATH` | `{db_dir}/cvm_financials.db` | Override SQLite file path |
| `CVM_OUTPUT_DIR` | `{data}/output` | Override output directory |
| `CVM_LOG_DIR` | `{data}/output/logs` (dev) · `{data}/logs` (frozen release) | Override log directory |
| `CVM_CACHE_DIR` | `{data}/cache` | Override cache directory |
| `VITE_MOCK_BRIDGE` | — | Set to `1` (dev only) to activate the in-process mock bridge; set automatically by `npm run dev:mock` via `.env.mock` |

## F5 / reload behavior in dev mode

In `--dev` mode, the app loads the Vite dev server (`http://127.0.0.1:5173`).

- **F5 / browser reload** reloads the Vite frontend inside the pywebview window.
- The Python backend and bridge stay alive — they run in the same process and are
  not affected by a page reload.
- After reload, the frontend's `whenBridgeReady()` waits for the `pywebviewready`
  event, which pywebview fires again on every page load. The bridge reconnects
  automatically.
- The latest database state is read fresh on every query — no stale in-memory
  data survives a reload.

If a refresh job was running when you reloaded, the UI will recover its state on
the next `get_app_status` or `get_database_diagnostics` call (both are polled).

Note: pywebview's DevTools can be opened with `--debug`. Press F12 after the
window opens.

## Concurrency and lock file

At startup, `desktop/app.py` acquires a JSON lock file at
`{data_dir}/runtime.lock`. The lock stores the PID, runtime mode, start time,
and app version of the owning process. On graceful exit the file is deleted.

**Stale lock recovery**: if a lock file exists but the recorded PID is no longer
alive, the lock is taken over automatically and the event is logged.

**Concurrent conflict**: if a lock file exists and the recorded PID is alive
(another CVMAnalytics process is running against the same directory), the app
starts in **restricted mode**:

- `CVMANALYTICS_CONCURRENT_LOCK_DETECTED=1` is set in the process environment.
- All destructive bridge methods (`start_data_update`, `reset_local_database`,
  `start_onboarding_setup`, etc.) return `{"ok": false, "status": "blocked"}`.
- The restriction persists for the lifetime of the process.
- The Status page shows `Write mode: read-only` and `Lock: locked by another
  process`.

## Write mode in dev+release-data

When desktop dev points at the release `Documents\CVMAnalytics\` directory, the
app sets `CVMANALYTICS_USE_RELEASE_DATA=1`. To prevent accidental mutations to
real user data, all destructive bridge calls are blocked by default:

```
{"ok": false, "status": "blocked", "status_reason_code": "release_data_write_blocked"}
```

To opt in to writes explicitly:

```powershell
$env:CVMANALYTICS_ALLOW_RELEASE_DATA_WRITES = "1"
.\scripts\release\dev-desktop-release-data.ps1
```

The release app (packaged, `sys.frozen=True`) is never affected — it always has
write access regardless of these env vars.

## Dev diagnostics and safety controls

The **Status page** (`/status`) shows the active data directory and database path
under "Runtime diagnostics". When `CVMANALYTICS_USE_RELEASE_DATA=1` is active:

- The **Mode** field shows `vite dev (release data)`.
- An amber warning banner appears in the Runtime card.
- The **Write mode** field shows `read-only` (amber) unless writes are explicitly
  allowed via `CVMANALYTICS_ALLOW_RELEASE_DATA_WRITES=1`.
- The **Lock** field shows the lock state (`locked by this process`, `locked by
  another process`, or `stale lock recovered`).
- The "Runtime diagnostics" card lists a warning that destructive actions affect
  real user data.

## Testing workflows

### Run dev against shared Documents data

```powershell
.\scripts\release\dev-desktop.ps1
```

Same database as the installed app. Check the Status page to confirm the path.
Destructive bridge actions are blocked by default in dev shared-data mode.

### Run dev against isolated data

```powershell
$env:CVM_DATA_DIR = "$PWD\data"
python -m desktop.app --dev
```

Safe for resets. Data under `{repo}/data/` is not shared with the release app.

### Reset only onboarding state (explicit isolated data)

Delete `{repo}/data/onboarding_state.json`, then reload the app.

### Reset explicit isolated dev database

Delete `{repo}/data/db/cvm_financials.db`. The app will re-initialize schema on
next start.

### Verify active data directory

Open the Status page (`/status`) → "Runtime diagnostics" → "Data directory".

### Reload UI

Press F5 inside the pywebview window while running `--dev`.

## Known limitations

- **Browser-only preview** (`npm run dev` in `apps/desktop-web`) has no bridge.
  All `window.pywebview.api` calls fail. The Status page shows a browser fallback
  banner. Use `npm run dev:mock` for fixture-backed UI development, or
  `python -m desktop.app --dev` for realistic testing.
- `CVMANALYTICS_USE_RELEASE_DATA` does not copy or migrate data — it just points
  the dev app at the existing release directory. If the release app has never run,
  that directory may not exist yet.
- **Concurrent access is read-only-blocked, not prevented.** If both the dev app
  and the release app run simultaneously against the same directory, the later
  starter enters restricted mode (all writes blocked). SQLite WAL mode reduces
  read contention, but running both apps concurrently is still inadvisable for
  writes — stop one process first.
- Mock fixture data does not reflect live database state. It is fixed at file
  creation time. Do not use `npm run dev:mock` to validate data-layer behavior.
