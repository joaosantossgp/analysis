# Dev Runtime and Data Paths

## Active frontend

| Location | Purpose |
|----------|---------|
| `apps/desktop-web/` | Vite + React SPA — the only active frontend |
| `apps/desktop-web/src/` | TypeScript/TSX source |
| `apps/desktop-web/dist/` | Built static bundle (gitignored; generated by `npm run build`) |

Do not modify code under `apps/api/` for desktop work — that is a separate FastAPI service.

## Active backend / bridge

| Location | Purpose |
|----------|---------|
| `desktop/app.py` | pywebview entry point; path setup; window creation |
| `desktop/bridge.py` + `desktop/bridge_api/` | `CVMBridge` public entry point and domain mixins exposed to the JS frontend |

## Data directory — release app

Without path overrides, the packaged release app (`CVMAnalytics.exe`) stores
runtime data under:

```
%USERPROFILE%\Documents\CVMAnalytics\
├── db\
│   └── cvm_financials.db      ← SQLite database
├── output\                    ← Excel exports
├── logs\                      ← Refresh logs
├── cache\                     ← Active universe cache, health snapshots
└── backup\                    ← Automatic pre-migration backups
```

This path is resolved by `_user_data_root()` in `desktop/app.py` and injected as
`CVM_DATA_DIR` (and related `CVM_*` vars) by `_configure_bundled_data_paths()`,
which configures both source and packaged launches with different defaults.
Startup work (database initialization, classification sync, local CNPJ
enrichment) then reads its paths from `build_settings()`, never from
`_user_data_root()` directly, so a source run only touches its active data root
and never the installed app's database.

Override with `CVMANALYTICS_DATA_DIR` env var to redirect the release app to a
different location (useful for staging or operator installs).

## Data directory — dev mode (default: shared dev data)

Without path overrides or release-data opt-in, `python -m desktop.app --dev`
uses the **shared dev data** of the main checkout, also when it is launched from
a git worktree:

```
<main checkout>\data\dev-runtime\
├── db\
│   └── cvm_financials.db
│   └── energy_kpis.db
├── input\                     ← downloaded CVM files (about 2 GB)
├── output\
├── logs\
├── cache\
└── raw\
```

The main checkout is the first entry of `git worktree list`. A new worktree
therefore opens with the companies and statements already downloaded. When git
cannot list the worktrees, the checkout uses its own `data\dev-runtime`.

This root persists across launches and accepts updates separately from the release
database. Existing path overrides can still redirect individual files. The dev
panel keeps its dev data backups next to it, in `data\dev-runtime.backup\`
(see [dev data actions](#dev-data-actions)).

### Isolated dev data (data-sensitive worktree)

A worktree whose work could alter or break shared dev data runs on **isolated
dev data**. The agent decides this from the rule in
[`AGENTS.md`](../AGENTS.md#5-workflow) ("Dev data in worktrees"); there is no UI
toggle. From the worktree:

```powershell
.\.venv\Scripts\python.exe scripts/dev/isolate_dev_data.py              # own databases, shared downloads
.\.venv\Scripts\python.exe scripts/dev/isolate_dev_data.py --full-copy  # own copy of everything
```

The script ([`scripts/dev/isolate_dev_data.py`](../scripts/dev/isolate_dev_data.py),
logic in [`desktop/dev_data.py`](../desktop/dev_data.py)):

- only reads shared dev data, and copies every database under `db\` with the
  WAL-safe copy, so it is safe while dev mode is open on shared dev data;
- writes the git-ignored marker `.dev-data-isolated` at the worktree root
  (content `isolated` or `full-copy`) after the copy succeeded;
- refuses to run on the main checkout, and refuses to replace dev data the
  worktree already holds unless `--force` is passed.

| Marker | Data root | Databases | Downloaded CVM files (`input\`) |
|---|---|---|---|
| none | `<main checkout>\data\dev-runtime` | shared | shared |
| `isolated` | `<worktree>\data\dev-runtime` | own copy | shared (`CVM_INPUT_DIR` points at the shared folder) |
| `full-copy` | `<worktree>\data\dev-runtime` | own copy | own copy |

Output, logs and cache follow the data root. Dev mode reads the marker when the
app starts; restart it after running the script. Delete the marker to return to
shared dev data (the worktree's own copy stays on disk until deleted by hand).
A marker on the main checkout is ignored. With `isolated`, a refresh still
writes downloaded files into the shared folder; use `--full-copy` when the work
changes those files.

`scripts/release/dev-desktop.ps1` sets `CVM_DATA_DIR` to `data\dev-runtime` of
the checkout it runs in. That is an explicit override: from a worktree it uses
the worktree's own folder and ignores the marker.

`CVM_DATA_DIR` takes precedence over default and release-data root selection.
It does not redirect every output path; see the
[development guide's path rules](development.md#data-paths).

## Dev commands

### Default dev (shared dev data)

```powershell
# From the main checkout or any git worktree
python -m desktop.app --dev

# Or use the convenience script (pins this checkout's own data\dev-runtime)
.\scripts\release\dev-desktop.ps1
.\scripts\release\dev-desktop.ps1 --debug    # opens DevTools
```

Data lives in `<main checkout>\data\dev-runtime` unless the worktree is
[data-sensitive](#isolated-dev-data-data-sensitive-worktree). Updates and
exports are enabled.

### Dev with custom data directory

```powershell
$env:CVM_DATA_DIR = "C:\path\to\your\test-data"
python -m desktop.app --dev
```

Use this for throwaway data, destructive experiments, or fixtures that must
not touch shared dev data or the Documents database.

### Vite-only (browser preview, no bridge)

```powershell
cd apps/desktop-web
npm run dev
```

Serves the browser preview at `http://127.0.0.1:5173` by default, moving to a free
port if needed. Open the URL printed by Vite. The Python bridge is unavailable;
the adapter reports a `BridgeError` for real bridge calls. Use mock mode for
fixture-backed layout work.

### Vite-only with mock bridge (browser preview + fixture data)

```powershell
cd apps/desktop-web
npm run dev:mock
```

Runs the Vite dev server with `VITE_MOCK_BRIDGE=1`. All `callBridge()` calls are
routed to an in-process fixture implementation (`src/lib/bridge/mock.ts`) instead
of `window.pywebview.api`. The fixture provides:

- 6 companies: complete, partial, failed, no_history, and unmapped variants
- One running and one completed refresh job
- Financial KPIs and statement matrices for two companies
- Base health snapshot at 70% coverage
- Local database state scenarios (`localStorage.cvm_mock_local_database`), update settings, sector directory

**This mode is dev-only.** The mock bridge module is dead-code-eliminated from
production builds (Vite tree-shakes `import.meta.env.DEV === false` paths). A
runtime guard inside `mock.ts` also throws if somehow loaded in a non-dev build.

The Status strip shows **BRIDGE · MOCK** in violet and Settings -> Diagnostics shows
`Mode: mock (fixture)` in the Runtime card.

## F5 / reload behavior in dev mode

In `--dev` mode, the app starts its own Vite server on the first free loopback
port from `5173` through `5199` and opens that URL in pywebview. It removes
inherited `VITE_MOCK_BRIDGE` from the spawned process environment. Keep mock
configuration confined to `.env.mock` and the browser `dev:mock` command.

- **F5 / browser reload** reloads the Vite frontend inside the pywebview window.
  It does not restart Python; only a Python source change does (see below).
- The Python backend and bridge stay alive — they run in the same process and are
  not affected by a page reload.
- After reload, the frontend's `whenBridgeReady()` waits for the `pywebviewready`
  event, which pywebview fires again on every page load. The bridge reconnects
  automatically.
- The latest database state is read fresh on every query — no stale in-memory
  data survives a reload.

If a refresh job was running when you reloaded, the UI will recover its state on
the next `get_app_status` or `get_database_diagnostics` call (both are polled).

Note: pywebview's DevTools can be opened with `--debug`. Press F12 after the
window opens.

## Auto-restart on Python changes (dev supervisor)

`python -m desktop.app --dev` starts a dev supervisor
([`desktop/dev_supervisor.py`](../desktop/dev_supervisor.py)), which runs the
app as a child process. Source mode only: the packaged app and launches without
`--dev` have no supervisor.

- **Trigger.** The supervisor polls the `*.py` files under `desktop/` and `src/`
  twice a second (standard library, no file-watcher dependency). After a change
  it waits for one second without further changes, so a burst of saves causes
  one restart.
- **Restart.** The supervisor asks the child to stop by closing its stdin. The
  child saves its route and window geometry, closes its windows, releases the
  runtime lock and stops its Vite server. A child that does not exit within 10
  seconds is killed with its process tree; the next start then recovers a stale
  lock.
- **Continuity.** The new child reopens on the last route with the same size
  and position. The route is stored relative to the origin, so it survives a
  different Vite dev port. Browser storage is tied to the origin and is not
  carried over.
- **Failed start.** If the changed code fails to start, the traceback stays in
  the terminal, the supervisor reports the exit code and keeps running, and the
  next Python change starts the app again. Press Ctrl+C in the terminal to quit
  while no window is open.
- **Ending dev mode.** Closing the main window (child exit code 0) ends the
  supervisor.
- **Hold still.** The [dev panel](#dev-panel) turns automatic restart off and
  on and restarts the app on demand. With automatic restart off, Python changes
  are counted but not loaded until you restart; a change after a failed start
  still starts the app, because there is no window to restart from. The
  setting lasts across app restarts but not across dev sessions: every new
  `--dev` launch starts with automatic restart on.
- **Stop that fails.** If the old app is still running after the kill, the
  supervisor starts no new app (it would fight the old one for the runtime lock
  and port), says so in the terminal, and retries the stop on the next poll. A
  new app that cannot be spawned at all is reported the same way; the next
  Python change or restart request tries again.
- **UI changes** under `apps/desktop-web` keep updating through Vite HMR without
  a restart.

Limits:

- Only `*.py` files under `desktop/` and `src/` trigger a restart. Changes to
  `requirements.txt`, `apps/api`, or data files do not.
- A change to `desktop/dev_supervisor.py` or to the launcher block at the top of
  `desktop/app.py` restarts the child, but the running supervisor keeps its old
  code. Relaunch dev mode to pick it up.
- Secondary windows (Excel Mapping) are not reopened. A maximized window comes
  back at the same bounds as a normal window, and a minimized one comes back at
  its last saved geometry.
- Each restart starts a new Vite dev server; the port can change within
  `5173`–`5199`.

## Worktree switch

The [dev panel](#dev-panel)'s **Worktrees** section lists every git worktree of
the repository, main checkout first. The list comes from
`git worktree list --porcelain`, so worktrees created by any tool appear; a
worktree removed on disk is left out. Each row shows the folder name, the branch
(or "Detached HEAD") and the flags **Active** (the window runs it),
**Isolated data** (a [data-sensitive worktree](#isolated-dev-data-data-sensitive-worktree))
and **Dependencies differ**. Code:
[`dev_data.list_worktrees`](../desktop/dev_data.py),
[`dev_bootstrap.dependency_differences`](../desktop/dev_bootstrap.py) and the
supervisor's `switch_worktree` request in
[`desktop/dev_supervisor.py`](../desktop/dev_supervisor.py).

- **Environment.** A worktree runs on the environment of the checkout dev mode
  was launched from (the main checkout in normal use), its `.venv` interpreter
  and its `apps\desktop-web\node_modules`, wherever its `requirements.txt` and
  `apps\desktop-web\package-lock.json` have the fingerprints stored in that
  environment's bootstrap stamps (`.venv\.cvmanalytics-dev-bootstrap.json`,
  `node_modules\.cvmanalytics-dev-bootstrap.json`). A part whose manifest
  differs runs on the worktree's own install instead: its own `.venv`, its own
  `npm ci`. The row then says "Dependencies differ" and names the files; while
  that own install is missing or stale (its stamps do not match its manifests)
  the button reads **Install & switch** and the row says the switch installs
  them first (about 1-2 minutes).
- **Switch.** The supervisor stops the app and starts it again on the chosen
  worktree, on the same route and window geometry:
  - Python: `python -c "from desktop.app import main; main()" --dev` in the
    worktree, with the launch checkout's interpreter, or with the worktree's
    own `.venv\Scripts\python.exe` when its `requirements.txt` differs. The
    worktree's code is imported, and its own bootstrap does not run, whatever
    version of it the branch has.
  - Frontend, matching lockfile: on the first switch, the launch checkout's
    `node_modules` is hard linked file by file into the worktree's git-ignored
    `apps\desktop-web\node_modules` (Vite caches left out; a copy across
    volumes). Vite then runs from the worktree as from a normal install. Not a
    junction or `NODE_PATH`: Vite and its config resolve packages by walking up
    from the worktree, which `NODE_PATH` does not change, and `npm ci` empties a
    linked `node_modules` folder, so a junction would wipe the launch checkout's
    copy. Files rewritten in place, npm's hidden lockfile
    (`node_modules\.package-lock.json`, which any npm command in the worktree
    rewrites) and the bootstrap stamp, are copied instead of linked. Deleting
    the worktree, or npm in it, removes only the worktree's own link names; the
    launch checkout is only read. The linked stamp makes later switches skip
    this step. A `node_modules` the bootstrap or a switch installed for another
    lockfile (its stamp says so) is deleted and linked again, never mixed; one
    from a plain `npm ci` (no stamp) is kept and only completed with links, as
    an agent may be running Vite or tests from it.
  - Frontend, differing lockfile: the worktree's own `npm ci` (see below).
  - Dev data follows the worktree: shared dev data, or its own isolated dev
    data when it carries the marker.
  - Automatic restart then watches `desktop\` and `src\` of the active worktree
    only.
- **Install.** A switch to a worktree whose own install is missing or stale
  first installs it with the dev bootstrap
  ([`dev_bootstrap.provision`](../desktop/dev_bootstrap.py)), on a background
  thread of the supervisor, while the current window stays open and usable:
  - `requirements.txt` differs: `python -m venv --copies <worktree>\.venv` (when
    missing), then `pip install -r requirements.txt` with that interpreter.
  - The lockfile differs: the worktree's `apps\desktop-web\node_modules` is
    deleted name by name (it may hold the hard links above; deleting unlinks,
    it never writes a file), then `npm ci` there.
  - Each part writes the worktree's own bootstrap stamp when done, so a later
    switch to the worktree with unchanged manifests installs nothing and is
    immediate. The launch checkout is never written.
  - Progress: the Worktrees section shows "Installing dependencies for
    <worktree>" with the current step ("Creating Python environment",
    "Installing Python packages", "Installing frontend packages") and the
    elapsed time, read from the supervisor's status every second. The
    terminal prints each step. Other switches are refused until it finishes.
  - Done: the window closes and reopens on the worktree.
  - Failed: the window stays on the worktree it was on. The Worktrees section
    shows "Installing dependencies for <worktree> failed" with the failed
    command, its exit code and the last 40 lines of its output; the terminal
    prints the same. Switching again retries; the parts already installed are
    skipped.
  - Measured on the owner's machine (pip and npm caches warm): about 70 seconds
    for a new `.venv` plus `npm ci`.
- **Failed switch.** If the app exits with an error within 60 seconds of
  starting on the switched-to worktree, or cannot be spawned, the supervisor
  returns to the previous worktree and its environment. The traceback stays in
  the terminal and the Worktrees section says "Switching to <worktree> failed:
  …". A crash after that is an ordinary
  [failed start](#auto-restart-on-python-changes-dev-supervisor).
- **Removed worktree.** When the active worktree's `.git` file disappears
  (`git worktree remove`), the supervisor falls back to the launch checkout and
  the Worktrees section says so.
- **Start.** Every `--dev` launch starts on the checkout it was launched from.
- **Channel.** `dev_list_worktrees` returns the rows (each with
  `dependency_differences` and `installs_needed`) plus the supervisor's last
  `worktree_notice`, its `notice_detail` (`command`, `exit_code`, `output` of a
  failed install) and the `install` under way (`worktree`, `name`, `step`,
  `started_at` in Unix seconds), or null. `dev_switch_worktree` refuses the
  packaged app, a missing supervisor, an unknown or removed worktree, the
  window's own worktree and a switch while an install runs; otherwise it
  queues `{"action": "switch_worktree", "path": ...}` and returns once the
  supervisor publishes either the new `worktree` (`installing: false`; the
  window closes right after) or the `install` for it (`installing: true`). The
  supervisor checks the request again.

Limits:

- A worktree whose branch predates the Worktrees section has no way to switch
  back from its window: close the window and run dev mode again.
- Dev mode launched from a worktree (not the normal case) runs every other
  checkout, the main checkout included, on that worktree's environment, and
  links its `node_modules` into them.
- The 60-second rule is a time limit, not a signal from the app: a switched-to
  app that takes longer to fail stays on that worktree.
- Dependencies are compared when you switch. A worktree whose manifests change
  while the window runs it keeps running on the environment it was switched
  with until you switch again; the list then flags what a switch would install.
- Hard links share file content: a tool that edits a package file in place
  inside a linked `node_modules` (rather than replacing it, as npm does for
  package files) edits the launch checkout's copy too.
- Closing the window during an install ends dev mode without waiting for it; a
  `pip` or `npm` process already started may keep running until it finishes.
  The next switch completes the install, since its stamp was not written.

## Dev panel

In dev mode a small floating dot sits at the bottom right of the window. Click
it or press `Ctrl+Shift+D` to open the dev panel; press Escape, `Ctrl+Shift+D`
or the close control to close it. Drag the dot anywhere; its position is kept
for the next launch. The packaged app has no dot, panel or shortcut: the panel
is compiled only into Vite dev builds and its bridge methods refuse with
`status_reason_code: "dev_mode_only"` when the app is frozen.
(`Ctrl+Alt+D` still opens `/dev/design-system`.)

| Section | Shows / does |
|---|---|
| Context | Worktree (and whether it is the main checkout), branch, commit, uncommitted changes, data mode with an "isolated data" indicator, data path. Missing git values stay `—` with the git error. |
| Worktrees | Every git worktree with its branch and the Active, Isolated data and Dependencies differ flags; switches the window to a worktree, installing its own dependencies first when they differ ("Install & switch", with the current step and elapsed time; a failed install shows its command and output). See [worktree switch](#worktree-switch). The list scrolls past about five rows. Switching is disabled without the dev supervisor. |
| Restart | "Restart app" and the "Restart automatically" switch; how many Python changes the window has not loaded yet. Disabled when the app runs without the dev supervisor. |
| Dev data | Size, path and backup of the database, the downloaded CVM files and everything; "Move to backup", "Restore backup" and "Delete" for each, and the outcome of the last action. See [dev data actions](#dev-data-actions). |
| Tools | Link to the `/dev/data-ops` page (opening it from the panel sets its `cvm_dev_tools` flag). |

Data modes: `shared`, `isolated`, `full-copy` (see
[isolated dev data](#isolated-dev-data-data-sensitive-worktree)),
`installed-app` (`CVMANALYTICS_USE_RELEASE_DATA=1`) and `custom` (an explicit
`CVM_DATA_DIR`).

Code: one file per section in
[`apps/desktop-web/src/components/dev-panel/sections/`](../apps/desktop-web/src/components/dev-panel/sections/);
a new `*Section.tsx` file that exports `section` is picked up without editing a
shared list. Bridge methods `dev_get_context`, `dev_restart`,
`dev_set_auto_restart`, `dev_list_worktrees`, `dev_switch_worktree`,
`dev_get_data_info`, `dev_move_data_to_backup`, `dev_restore_data_backup` and
`dev_delete_data` live in
[`desktop/bridge_api/dev.py`](../desktop/bridge_api/dev.py); browser mock
scenarios (`localStorage.cvm_mock_dev_context` = `isolated` or `error`;
`localStorage.cvm_mock_dev_data` = `unavailable`; a switch to the mock
`612-own-dependencies` worktree simulates a 12-second install, and
`localStorage.cvm_mock_dev_install` = `fail` makes it fail) in
[`mock.dev.ts`](../apps/desktop-web/src/lib/bridge/mock.dev.ts).

**Request channel.** The app cannot restart itself, so the bridge asks the dev
supervisor. The supervisor creates a temporary control directory and passes it
to the app as `CVMANALYTICS_DEV_CONTROL_DIR`. The app queues requests as JSON
files in `requests\` (`{"action": "restart"}`,
`{"action": "set_auto_restart", "enabled": false}`); the supervisor takes them
on each poll, oldest first, and publishes `status.json`
(`auto_restart`, `pending_changes`, and the active `worktree` with the last
`worktree_notice`, its `worktree_notice_detail` and the dependency `install`
under way). Unknown requests, and request files that
are not a JSON object, are larger than 64 KB or nest too deeply, are reported
in the terminal and ignored. Restart requests queued while a restart is under way are
answered by that restart. A data action is
`{"action": "data_action", "operation": "backup" | "restore" | "delete", "target": "db" | "input" | "all", "mode", "data_root", "shared_root"}`;
its outcome goes to `data_action.json` in the same directory. A worktree
switch is `{"action": "switch_worktree", "path": ...}` (see
[worktree switch](#worktree-switch)). A data action and a switch queued
together are both done in one restart, and a refused switch does not drop the
data action.

### Dev data actions

The "Dev data" section resets dev data to test the first-run download again,
restores the previous state, or frees disk space. Code:
[`desktop/dev_data_actions.py`](../desktop/dev_data_actions.py) (file
operations and refusals), the `data_action` request in
[`desktop/dev_supervisor.py`](../desktop/dev_supervisor.py), and
[`DevDataSection.tsx`](../apps/desktop-web/src/components/dev-panel/sections/DevDataSection.tsx).

| Target | Shared dev data | Isolated dev data | Full copy |
|---|---|---|---|
| Database | `<main>\data\dev-runtime\db` | `<worktree>\data\dev-runtime\db` | `<worktree>\data\dev-runtime\db` |
| Downloaded CVM files | `<main>\data\dev-runtime\input` | `<main>\data\dev-runtime\input` (shared folder) | `<worktree>\data\dev-runtime\input` |
| Everything | `<main>\data\dev-runtime` | `<worktree>\data\dev-runtime` (downloads stay shared) | `<worktree>\data\dev-runtime` |

| Action | Does |
|---|---|
| Move to backup | Renames the target into its **dev data backup** slot, `<data root>.backup\<target>` next to the data root that holds it (for example `<main>\data\dev-runtime.backup\db`). One slot per target: a newer backup deletes the older one. |
| Restore backup | Renames the backup back into place; current data of that target is deleted. |
| Delete | Deletes current data of the target after the target name (`db`, `input`, `all`) is typed again. The backup is kept. |

- **App stopped.** The bridge checks the action and queues it; the dev
  supervisor stops the app, performs the action, then starts the app again, so
  no database handle is open. After the database is moved or deleted
  (`db` or `all`), the app reopens on its start page, the empty first-run
  state; otherwise on the last route.
- **Confirmation.** Each action asks first and states the target, its path and
  size, the backup path and size, what is lost, and, for shared dev data, that
  the action affects every worktree that uses it.
- **Atomic, rolled back.** Every step is a rename on one volume. Before a
  rename replaces something, the old data is renamed aside (`.trash-*` in the
  backup folder) and removed only after the main rename succeeded; when the
  main rename fails, the aside data is renamed back and the result says
  "Nothing was changed". A locked file (`PermissionError`) is retried twice,
  half a second apart. If removing the aside data fails, the action still
  succeeded and the result names the folder to delete by hand.
- **Active worktree.** After a [worktree switch](#worktree-switch) the actions
  work on the dev data of the worktree the window runs (its isolated dev data,
  or the shared dev data), and the app restarts on that worktree.
- **Outcome.** The terminal and the section's "Last action" line show what
  happened; a failure is shown as an error with its reason. The outcome is kept
  for the whole dev session, across restarts and worktree switches.
- **Refused** (section shows the reason; bridge returns
  `status_reason_code: "dev_data_actions_unavailable"`; the supervisor checks
  again): installed-app data (`CVMANALYTICS_USE_RELEASE_DATA`), a custom
  `CVM_DATA_DIR`, a data root that is, contains or lies inside
  `%USERPROFILE%\Documents\CVMAnalytics`, `CVMANALYTICS_DATA_DIR` or
  `%LOCALAPPDATA%\CVMAnalytics`, any folder other than
  `<git checkout>\data\dev-runtime`, and the packaged app (`dev_mode_only`).
- **In use.** An action is refused while another live process holds the
  `runtime.lock` of the data root holding the target (for example the main
  checkout's dev mode window, for shared dev data). Dev mode windows of other
  data-sensitive worktrees still read the shared downloads without holding
  that lock; close them before acting on downloaded CVM files.
- Per-path overrides (`CVM_DB_DIR`, `SQLITE_PATH`, `CVM_INPUT_DIR`) are not
  followed: the targets are always derived from the data root.
- `data\dev-runtime.backup\` is git-ignored.

## Concurrency and lock file

At startup, `desktop/app.py` acquires a JSON lock file at
`{data_dir}/runtime.lock`. The lock stores the PID, runtime mode, start time,
and app version of the owning process. On graceful exit the file is deleted.

The lock follows the effective data root, not the launching checkout. Two dev
mode processes on shared dev data (for example one from the main checkout and
one from a worktree) therefore meet at
`<main checkout>\data\dev-runtime\runtime.lock` and the second one records the
conflict. A data-sensitive worktree locks its own data root.

**Stale lock recovery**: if a lock file exists but the recorded PID is no longer
alive, the lock is taken over automatically and the event is logged.

**Concurrent conflict**: if a lock file exists and the recorded PID is alive
(another CVMAnalytics process is running against the same directory), the
launcher records the conflict:

- `CVMANALYTICS_CONCURRENT_LOCK_DETECTED=1` is set in the process environment.
- In explicit release-data dev, guarded bridge methods such as
  `start_data_update` and `reset_local_database` return a blocked response,
  even when release-data writes were requested.
- This bridge restriction is not a database-wide read-only guarantee. The current
  guard exempts the packaged app and dev mode on dev data (shared or isolated),
  and startup initialization still runs. Stop the other process before using
  shared data for writes.
- Settings -> Diagnostics reports the lock and write-mode status.

Implementation: [launcher](../desktop/app.py#L1182) and
[bridge write policy](../desktop/bridge_api/status.py#L1067).

## Write mode in dev+release-data

Explicitly setting `CVMANALYTICS_USE_RELEASE_DATA=1` (or using the shared-data
launcher) activates this mode; pointing `CVM_DATA_DIR` at Documents does not set
the flag automatically. Guarded bridge writes are blocked by default:

```
{"ok": false, "status": "blocked", "status_reason_code": "release_data_write_blocked"}
```

To opt in to writes explicitly:

```powershell
$env:CVMANALYTICS_ALLOW_RELEASE_DATA_WRITES = "1"
.\scripts\release\dev-desktop-release-data.ps1
```

The allow-writes flag does not bypass a concurrent lock conflict in release-data
dev. Packaged mode is exempt from this particular bridge guard; filesystem and
database errors can still prevent writes.

## Dev diagnostics and safety controls

**Settings -> Diagnostics** (`/settings/diagnostics`; `/status` redirects there)
shows the active data directory and database path
under "Runtime diagnostics". This is the effective data root: the main
checkout's folder on shared dev data, the worktree's own folder on isolated dev
data. When `CVMANALYTICS_USE_RELEASE_DATA=1` is active:

- The **Mode** field shows `vite dev (release data)`.
- An amber warning banner appears in the Runtime card.
- The **Write mode** field shows `read-only` (amber) unless writes are explicitly
  allowed via `CVMANALYTICS_ALLOW_RELEASE_DATA_WRITES=1` and no lock conflict is
  detected.
- The **Lock** field shows the lock state (`locked by this process`, `locked by
  another process`, or `stale lock recovered`).
- The "Runtime diagnostics" card lists a warning that destructive actions affect
  real user data.

## Testing workflows

### Run dev against shared Documents data

```powershell
.\scripts\release\dev-desktop-release-data.ps1
```

With no conflicting overrides, this selects the installed app's data. The script
does not clear `CVM_DATA_DIR` or per-path overrides; use a shell without them and
check Settings -> Diagnostics to confirm the paths. Guarded bridge writes are
blocked by default. See [shared-data dev](development.md#dev-with-installed-app-data).

### Run dev against an explicit data directory

```powershell
$env:CVM_DATA_DIR = "$PWD\data"
python -m desktop.app --dev
```

Safe for resets. Data under `{repo}/data/` is not shared with the release app
or with other worktrees.

### Reset the database of an explicit data directory

Delete `{repo}/data/db/cvm_financials.db`. The app will re-initialize schema on
next start.

### Verify active data directory

Open Settings -> Diagnostics (`/settings/diagnostics`) -> "Runtime diagnostics" -> "Data directory".
The same page also includes "Energy KPI Marts", which reports daily/preview
mart freshness, source high-water marks, and write-mode status without exact
raw hourly counts.

### Rebuild Energy KPI marts

CCEE hourly plant-parcel data can be much larger than the rest of the local
database. Daily plant charts and detail previews read rebuildable marts instead
of aggregating `ccee_plant_parcel_hourly` on demand.

For a targeted month:

```powershell
python scripts/data/rebuild_energy_marts.py --reference-month 2026-04
```

To rebuild only the compact source/submarket monthly summary:

```powershell
python scripts/data/rebuild_energy_marts.py --reference-month 2026-04 --source-submarket-only
```

To rebuild only the CEG hourly aggregation mart:

```powershell
python scripts/data/rebuild_energy_marts.py --reference-month 2026-04 --ceg-hourly-only
```

From Settings -> Diagnostics, use "Rebuild daily YYYY-MM" to rebuild only the
latest source month's daily mart plus the source/submarket summary mart. The UI
action is intentionally scoped and does not expose a one-click full historical
rebuild.

For a full maintenance rebuild:

```powershell
python scripts/data/rebuild_energy_marts.py --all
```

`--all` scans the full hourly table and can be slow on large user databases.
The daily mart rebuild is chunked by `reference_month` for progress visibility,
but it is still a maintenance job, not an app-startup path. Benchmark full
rebuilds on a copied database before running them on a user's live data root.
The rebuild preserves raw/source tables and records status in
`energy_mart_builds`.

`plant_parcel_source_submarket_monthly_mart` is a compact diagnostic/filter
summary at `reference_month + generation_source + submarket` grain. It exists so
broad source/submarket diagnostics can move away from raw hourly scans before
any future decision to remove raw-hourly source/submarket indexes.

Current schema initialization does not create the standalone
`idx_cppe_ref(reference_datetime)` index on `ccee_plant_parcel_hourly`. A copied
database benchmark in June 2026 showed the primary key can serve standalone date
lookups and `idx_cppe_parcel_ref` serves guarded drill-down, while removing the
redundant index frees about 2.22 GB before compaction. A later copied-DB
benchmark showed `idx_cppe_source` and `idx_cppe_submarket` are no longer used
by representative app-facing reads after the source/submarket mart cutover, and
dropping both would free about 2.67 GB of SQLite pages before compaction. Ad hoc
raw-hourly source/submarket filters would become full scans, so live removal is
a separate maintenance phase with rollback.

### Rebuild CVM financial marts

CVM financial statement rows remain in `financial_reports` as the audit source
of truth. Rebuildable query marts provide smaller read models for company
directory, period-completeness, and KPI-account paths.
After a successful rebuild, Companies list metadata, available-year lookups,
Company Detail latest-period metadata, KPI account reads, sector metric rows,
and historical indicator metrics read these marts by default. Fresh or unbuilt
profiles keep the canonical raw-query path until mart metadata reports a
successful rebuild. Depreciation/amortization extraction still reads
`financial_reports` because it depends on statement-line text matching that is
not yet represented in the KPI account mart.

For a full maintenance rebuild:

```powershell
python scripts/data/rebuild_cvm_financial_marts.py
```

To rebuild only one mart family:

```powershell
python scripts/data/rebuild_cvm_financial_marts.py --periods-only
python scripts/data/rebuild_cvm_financial_marts.py --directory-only
python scripts/data/rebuild_cvm_financial_marts.py --kpi-accounts-only
```

The rebuild is idempotent, preserves `financial_reports`, and records freshness
and source coverage in `financial_mart_builds`. The marts are maintenance/read
models only; Excel export and audit checks should still validate values against
the canonical financial rows until each read path is explicitly cut over.

Since #586, startup drops `idx_fr_cd_cvm`, `idx_fr_period_label`,
`idx_fr_cd_conta`, `idx_fr_cd_cvm_period_label` and
`idx_fr_cd_conta_period_label` (`DROP INDEX IF EXISTS`). `EXPLAIN QUERY PLAN` of
every `financial_reports` reader on a 436-company database used none of them,
and 126 read results were identical with and without them. `financial_reports`
keeps its unique key, `idx_fr_cd_cvm_stmt_year`, `idx_fr_cvm_year` and
`idx_fr_year_period` (sector reads use it when the marts are not built).
Dropping an index does not change data; the freed pages are reused by later
writes, and the file only shrinks after a `VACUUM`, which startup does not run.

### Compact Energy KPI database copy

After removing rebuildable indexes or caches, SQLite may show free pages without
shrinking the physical `.db` file. Create a compact validated copy with:

```powershell
python scripts/data/compact_energy_db.py `
  --database "$env:USERPROFILE\Documents\CVMAnalytics\db\energy_kpis.db" `
  --output "$env:USERPROFILE\Documents\CVMAnalytics\db\energy_kpis.compact.db"
```

The command uses SQLite `VACUUM INTO`, validates the compact copy with practical
read-only checks, and does not replace the live database. It exact-counts compact
mart/metadata tables and uses fast high-water checks for
`ccee_plant_parcel_hourly` by default. Add `--exact-hourly-count` only for
planned maintenance windows because it can scan the full hourly table. Add
`--full-integrity-check` only when a long SQLite `PRAGMA integrity_check` window
is acceptable. If `--database` is omitted, the script prefers
`%USERPROFILE%\Documents\CVMAnalytics\db\energy_kpis.db` when it exists, then
falls back to the configured development data path.

Do not swap the compact copy into the live data root while CVMAnalytics is
running. A future replacement flow must create a timestamped backup, verify the
copy, stop app processes, replace the database atomically, keep rollback
instructions, and run the packaged runtime smoke test.

## Known limitations

- **Browser-only preview** (`npm run dev` in `apps/desktop-web`) has no bridge.
  All `window.pywebview.api` calls fail. Settings -> Diagnostics shows a browser fallback
  banner. Use `npm run dev:mock` for fixture-backed UI development, or
  `python -m desktop.app --dev` for realistic testing.
- **Do not use `npm run dev:mock` for desktop dev.** It compiles the frontend
  with `VITE_MOCK_BRIDGE=1`, which deliberately routes bridge calls to fixtures
  instead of the packaged-app database.
- `CVMANALYTICS_USE_RELEASE_DATA` does not copy or migrate data — it just points
  the dev app at the existing release directory. If the release app has never run,
  that directory may not exist yet.
- **The lock is not a database-wide write barrier.** A detected conflict blocks
  guarded writes in release-data dev. It does not provide the same protection
  for the packaged app or for dev mode on shared or isolated dev data. Stop the
  other process before shared writes.
- **Isolated dev data still shares downloaded CVM files.** A refresh in a
  data-sensitive worktree writes into the shared `input\` folder; use
  `--full-copy` for work that changes those files.
- Mock fixture data does not reflect live database state. It is fixed at file
  creation time. Do not use `npm run dev:mock` to validate data-layer behavior.
