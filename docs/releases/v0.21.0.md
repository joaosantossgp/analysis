# CVMAnalytics v0.21.0 — Data Operations UX Release

`v0.21.0` rebuilds the local data lifecycle around three pillars:
**reliability**, **visibility**, and **coverage**. Updates now run with
visible progress, finished jobs invalidate the right caches without an
app restart, and a new Data Coverage page exposes every company that is
missing, partial, stale, failed, or unmapped — with one-click retry and
an "Ignore" workflow for cases that should not be acted on.

## Highlights

- **Update flow reliability.** Single-company refresh jobs (DB-worker
  path) and batch refresh jobs (`DesktopRefreshJobManager`) are now
  unified in `get_refresh_status` — Update Base sees both. Recent
  terminal DB-worker rows are included in history so a single-company
  retry from a company page does not disappear from view.
- **Real-time progress.** The Active Job Card uses the spec copy
  ("Atualizando dados das empresas / Processando X de N empresas /
  Etapa atual: …"), 2-second polling while active, 10-second idle. ETA
  is derived from guarded in-job rate, with fallback to recent comparable
  completed jobs and then the rolling 24h throughput estimate when
  confidence is sufficient.
- **Cache invalidation.** When a job transitions to a terminal state,
  every dependent query is invalidated exactly once (companies,
  company-info / years / kpis / statement, sectors, base-health,
  db-diagnostics, refresh-jobs, onboarding-state, app-status,
  data-coverage). Onboarding completion and single-company retries
  fan out the same set. No more stale dashboards after an update.
- **Data Coverage page (`/data-coverage`).** New route under the
  Database module. Computes per-company status from
  `financial_reports` (latest DFP / latest ITR), `company_refresh_status`
  (last attempt, last error, ignored flag), `companies` (registry), and
  `TICKER_MAP`. Surfaces:
  - 8 summary cards (total / complete / partial / sem dados / falha /
    desatualizado / mapeamento / ignorados).
  - 9 filter chips with live counts (todos / sem DFP / sem ITR / sem
    dados financeiros / desatualizados / falharam / ticker não mapeado /
    cadastro ausente / ignorados).
  - Search box (nome / CVM / ticker).
  - Table with status badge, latest DFP year, latest ITR period, last
    update timestamp, error preview, retry button, open-company link,
    and ignore/restore toggle.
- **Bulk ignore.** Row checkboxes + select-all + bulk bar ("Ignorar
  selecionadas" / "Restaurar selecionadas"). Sequential writes avoid
  hammering the SQLite write lock, and broad ignore actions ask for
  confirmation.
- **Virtualized Data Coverage table.** The table keeps the same columns,
  actions, filters, and status badges while only rendering the visible
  row window. This keeps scrolling smooth on large company universes.
- **Quick actions on Update Base.** Three buttons above the scope
  panel: Atualizar dados faltantes (mode=missing), Repetir falhas
  (mode=failed), Atualização completa (mode=full). Each dispatches with
  the current scope years + limit. Disabled while a refresh is active.
- **Update Base UX polish.** Header rewritten ("Mantém seu banco local
  do CVMAnalytics atualizado e mostra o histórico das execuções."),
  active card header flips to "Atualizando dados das empresas", last
  successful update surfaced under the header, tallies relabeled in
  PT-BR and now read from `RefreshResult.summary` + `planning_stats`.
- **Stage labels humanized.** `planning` → "Planejando",
  `download_extract` → "Baixando arquivos da CVM",
  `process_data` → "Processando dados",
  `persist_reports` → "Gravando no banco local",
  `finalizing` → "Finalizando".

## Fixed

- First-run/onboarding completion now invalidates the derived data views
  needed by Companies, Data Coverage, Base Health, diagnostics, and
  sectors.
- Single-company retry completion now refreshes Data Coverage and the
  related database health/diagnostic views without requiring reload.
- Terminal single-company jobs now appear in Update Base job history
  alongside batch jobs.
- Data Coverage freshness now updates after retries and onboarding.

## Improved

- ActiveJobCard ETA is intentionally approximate (`~45s`, `~8m`,
  `~1.4h`) and hides itself when timestamps, totals, rates, or
  historical samples are not trustworthy.
- Bulk ignored-company actions invalidate all data-operation query keys:
  `data-coverage`, `base-health`, `db-diagnostics`, companies, filters,
  refresh status, refresh jobs, and app status.

## Data model

Additive, non-destructive migration on `company_refresh_status`:

| Column | Type | Purpose |
|---|---|---|
| `ignored` | `INTEGER NOT NULL DEFAULT 0` | Hides the company from default Data Coverage filters; retry button disabled. |
| `ignored_at` | `TEXT` | ISO timestamp when the flag was set. |
| `ignored_reason` | `TEXT` | Optional operator note. |

Schema is applied via the existing `_ensure_refresh_status_schema`
`missing_columns` loop in [src/refresh_jobs.py](../../src/refresh_jobs.py).
Existing user DBs continue to work; the `get_data_coverage` query
introspects `PRAGMA table_info` so older DBs without the column return
`ignored=false` gracefully.

No other tables were touched. No data was rewritten.

## Bridge surface

- `get_data_coverage()` — new. Returns summary cards, filter counts,
  and sorted rows.
- `set_company_ignored({cd_cvm, ignored, reason?, company_name?})` —
  new. INSERT-or-UPDATE so flipping ignored on never-touched companies
  works. Invalidates Python read caches.
- `get_refresh_status({})` — now unions active and recent-terminal
  rows from the `refresh_jobs` table, in addition to JSON-batch jobs.
- `get_refresh_status({job_id})` — falls through to a `refresh_jobs`
  table lookup when the JSON store has no match.

## Manual test plan

**Fresh database:**

1. Delete `Documents/CVMAnalytics/db/cvm.sqlite` (or run on a clean
   user-data root). Launch the packaged exe.
2. First-run onboarding selects a universe → starts the initial
   download → progress card streams stage + processed count.
3. After completion, Companies dashboard shows fresh counts without a
   restart.

**Existing database:**

1. Launch packaged exe. Navigate to Database → Atualizar base.
2. Click "Repetir falhas" (or "Atualizar dados faltantes").
3. Active Job Card shows "Processando X de N empresas / Etapa atual:
   Baixando arquivos da CVM". Tempo column shows elapsed and ETA.
4. After completion, history list shows the new entry as "Concluída"
   with elapsed time. Companies list refetches.

**Failure case:**

1. With a known-failing CVM code, hit Atualizar from
   CompanyRefreshPanel.
2. Job appears in Update Base history as "Falha".
3. Open Data Coverage → company is now in "Última atualização falhou"
   filter with the error preview.
4. Click "Atualizar" on the row → new job dispatched; on success row
   moves out of the failed bucket.

**Missing data:**

1. Open Data Coverage. Filter chips counts match summary cards (within
   the rule that "stale" is included only in its own card).
2. Switch to "Sem DFP" → table reflows to those companies only.
3. Search "PETR" → table further narrows.
4. Select 5 rows → bulk bar appears → "Ignorar selecionadas" → rows
   vanish from default filters; "Ignorados" filter shows them.
5. "Restaurar selecionadas" returns them to their original buckets.

**Data Coverage performance:**

1. With hundreds or thousands of active companies, table scroll remains
   smooth; filters and search continue narrowing the row set.
2. Select multiple rows → bulk bar appears → "Ignorar selecionadas" →
   counts update and default filters hide the rows.
3. Switch to "Ignorados" → select rows → "Restaurar selecionadas" →
   counts update and rows return to their actionable buckets.

## Known limitations

- DB-worker history is capped at last 10 terminal rows in the unified
  list. Older runs remain in the `refresh_jobs` table and are still
  reachable per-company via CompanyRefreshPanel.
- Bulk ignore is sequential (one SQLite write per company) to avoid
  SQLite write-lock pressure. Large selections are allowed but confirmed
  before applying.
- No persistent per-event log (`sync_job_events`-style table). The
  existing `log_lines` array on batch jobs + `progress_message` on DB
  jobs + `refresh_runs.jsonl` terminal log cover the audit need.
- ETA uses guarded in-job rate, recent comparable completed jobs, then
  the rolling 24h throughput estimate; first-ever run on a clean DB has
  no fallback and shows elapsed only.
